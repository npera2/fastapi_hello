## 排查：GET /book/count 返回 422 Unprocessable Entity

**根因：路由注册顺序问题，不是参数写错。**

`main.py` 里的注册顺序是：
```
/book/books        (85 行)
/book/book_select  (96 行)
/book/{book_id}    (112 行)   ← 动态路径
/book/count        (123 行)   ← 固定路径却排在后面
```

FastAPI **按注册顺序逐个匹配**。请求 `/book/count` 走到 `/book/{book_id}` 时，
**结构上匹配**（`count` 可以当参数值），于是停在那里尝试把 `"count"` 解析成 `book_id: int` →
解析失败 → 直接返回 422，**不再继续尝试后面的路由**。

**决定性证据**（实测抓到的 422 响应体）：
```json
{"detail":[{"type":"int_parsing","loc":["path","book_id"],
  "msg":"Input should be a valid integer, unable to parse string as an integer",
  "input":"count"}]}
```
`loc: ["path","book_id"]` 说明请求被 `/book/{book_id}` 捕获了，而不是 `/book/count`。

**openapi.json 里的 paths 顺序**（实测）也印证：
`/book/books` → `/book/book_select` → `/book/{book_id}` → `/book/count`

**为什么 `/book/books`、`/book/book_select` 没事**：它们注册在 `{book_id}` 之前，先被匹配到。

### 解决方案（已告知，用户表示"先不用修改代码"，尚未动手）

- **方案 A（最省事）**：把 `/book/count` 那段**整体上移**到 `/book/{book_id}` 之前。
- **方案 B（更规范）**：改路径避免同层级冲突，如 `/book/statistics/count` 或 `/book/count/total`。
- 不推荐给 `book_id` 加 `Path(ge=1)` 之类的约束——校验发生在"匹配成功之后"，
  依然会返回 422 而不是转给 `/book/count`。

### 通用预警（后续一定会踩）

**任何 `/xxx/{param}` 都会吃掉同层级中注册在它后面的所有字面路径。**
当前 `main.py` 里同样的隐患还有：
- `/news/{id}`（221 行）→ 以后写 `/news/latest` 会 422
- `/path_parameter/{num}`（158 行）→ 同层级加字面路径会 422
- `/exception/{id}`（233 行）→ 同上

**口诀：固定路径永远写在动态路径前面。**
